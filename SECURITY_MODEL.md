# Modello di sicurezza / Security Model

## Modello operativo / Operating model

LocalAgent Benchmark scopre i casi tramite manifesti locali, verifica gli input rispetto a Git, crea una fotografia unica di manifesti, prompt, fixture, grader, rubriche opzionali, `AGENTS.md`, `.gitignore` e policy di esecuzione, copia quella fotografia in repository Git dedicati, seleziona e registra la modalità sandbox, avvia Pi in modalità non interattiva e usa l'API OpenAI-compatible di Ollama su loopback. Ogni tentativo ha una directory Pi separata, uno scratch interno e conserva workspace, eventi, log, patch, valutazione, metriche e audit d'integrità. La dashboard ufficiale legge soltanto l'export pubblico ridotto: il launcher aggrega i run locali in memoria e li serve su loopback; un eventuale snapshot per `file://` viene generato localmente ed è ignorato da Git.

LocalAgent Benchmark discovers cases through local manifests, checks inputs against Git, creates one frozen snapshot of manifests, prompts, fixtures, graders, optional rubrics, `AGENTS.md`, `.gitignore`, and the execution policy, copies that snapshot into dedicated Git repositories, selects and records the sandbox mode, launches Pi non-interactively, and uses Ollama's OpenAI-compatible API over loopback. Each attempt has an isolated Pi configuration directory, an internal scratch area, and retains its workspace, events, logs, patch, grade, metrics, and integrity audit. The official dashboard reads only the reduced public export: the launcher aggregates local runs in memory and serves them on loopback; any `file://` snapshot is generated locally and ignored by Git.

La landing page è una superficie pubblica separata e puramente statica sotto `site/`. GitHub Pages pubblica soltanto quella directory: la pagina non legge run, repository locale o dashboard-data, non esegue il benchmark e non espone il server loopback della dashboard. I video sorgente locali restano ignorati fuori da `site/`; vengono pubblicati soltanto fotogrammi revisionati, privi di metadati superflui e ottimizzati. / The landing page is a separate, purely static public surface under `site/`. GitHub Pages publishes that directory only: the page does not read runs, the local repository, or dashboard data; it neither executes the benchmark nor exposes the dashboard's loopback server. Local source videos remain ignored outside `site/`; only reviewed, metadata-stripped, optimized frames are published.

Il percorso rapido è una UI Tkinter locale sopra gli stessi controlli del runner. Esegue prima `doctor`, richiede conferma, avvia `benchmark.py` con argomenti strutturati per le sole fasi `smoke`, `standard`, `full`, convalida gli artefatti prima di ogni promozione e apre la dashboard ufficiale soltanto dopo aver costruito il dataset ridotto in memoria. / The quick path is a local Tkinter UI over the same runner controls. It runs `doctor`, requires confirmation, launches only the `smoke`, `standard`, and `full` stages with structured arguments, validates artifacts before promotion, and opens the official dashboard only after building the reduced dataset in memory.

### Provider locali / Local providers

Ollama, LM Studio e il router llama.cpp sono processi host separati e non fidati rispetto al runner. `provider.url` accetta soltanto HTTP su loopback, senza path o credenziali; il client alternativo disabilita proxy e redirect e limita le risposte JSON a 1 MiB. La sandbox di Pi consente soltanto la porta configurata o il broker verso quella destinazione; il server dei modelli resta fuori dalla sandbox. La configurazione Pi per ogni task usa solo una chiave fittizia pari all'ID provider; server che richiedono autenticazione non sono supportati. Nessun GGUF viene copiato nella workspace o in `results/`. `provider.model_files` indica path locali letti dall'host per calcolare SHA-256; un path esplicito può trovarsi fuori dal repository. L'associazione tra ID modello, file e versione runtime è dichiarata dall'utente e non verificabile tramite le API locali. Per questo `compare` richiede versione dichiarata e hash GGUF sui nuovi provider, oltre alla normale compatibilità, ma tali dati non provano da soli che il server abbia caricato proprio quel file. I run senza provenienza completa restano ispezionabili individualmente. Preflight thinking, controllo Pi, snapshot, audit e report rimangono obbligatori.

Ollama, LM Studio, and the llama.cpp router are separate host processes outside the runner's trust boundary. `provider.url` accepts only HTTP loopback without paths or credentials; the alternative client disables proxies and redirects and caps JSON responses at 1 MiB. Pi's sandbox allows only the configured port or its fixed-destination broker; the model server itself remains outside the sandbox. Each task's Pi configuration contains only a dummy key matching the provider ID; authenticated servers are unsupported. No GGUF is copied into a task workspace or `results/`. The host reads explicit `provider.model_files` paths, which may be outside the repository, to calculate SHA-256. The mapping between served model ID, file, and user-declared runtime version cannot be verified through these local APIs. `compare` therefore requires version and GGUF digest for the new providers as well as normal compatibility, while these declarations alone do not prove which file the server loaded. Runs without full provenance remain individually inspectable. Thinking preflight, Pi contract, snapshot, audit, and reporting remain mandatory.

Il preflight verifica soltanto reasoning osservabile nell'output/API: se un server ignora `reasoning_effort` ma non espone tracce, la modalità interna resta non dimostrabile. LM Studio e llama.cpp possono cambiare comportamento tra versioni o template di modello; nessuno smoke reale sui nuovi provider è ancora stato eseguito. / The preflight checks only reasoning observable in output or API fields: a server that ignores `reasoning_effort` while hiding traces can leave its internal mode unverifiable. LM Studio and llama.cpp behavior can vary by version and model template; no real-model smoke test of the new providers has been completed yet.

## Asset e confini / Assets and boundaries

- Il repository del benchmark, `AGENTS.md` e i grader sono input fidati.
- Prompt e fixture inclusi nel repository sono input controllati, ma il loro contenuto viene comunque trattato come dati per il modello.
- Manifesti e rubriche descrivono il caso ma non concedono fiducia o permessi. Un grader importato è codice non fidato finché non viene revisionato; validazione e grading lo eseguono sul processo host.
- Le risposte del modello, gli argomenti tool e i file prodotti sono output non fidati.
- Il provider selezionato è un servizio locale separato; il confine HTTP è `provider.url`.
- Il filesystem esterno alla workspace del singolo caso non appartiene allo scope dell'agente.
- Per la dashboard, browser, estensioni browser e altri processi locali sono esterni al confine fidato. Il server accetta soltanto connessioni loopback e non trasforma il browser in un confine di isolamento per dati sensibili.
- Per la landing page, GitHub Pages, il browser del visitatore e i siti raggiunti tramite link espliciti sono esterni al confine fidato. I file pubblicati sotto `site/` sono per definizione accessibili a chiunque. / For the landing page, GitHub Pages, the visitor's browser, and sites reached through explicit links are outside the trust boundary. Files published under `site/` are public by definition.
- Per la GUI guidata, Tkinter e i launcher sorgente sono UI fidata; nomi e metadata dei modelli restituiti da Ollama, output dei processi e artefatti di run restano input locali da validare. Il manifesto guidato e le preferenze devono restare nella root del progetto. / For the guided GUI, Tkinter and the source launchers are trusted UI; model names/metadata from Ollama, process output, and run artifacts remain local inputs that require validation. The guided manifest and preferences stay inside the project root.

## Controlli implementati / Implemented controls

- Configurazione centrale validata all'avvio; URL, ID caso e modalità sandbox vengono controllati.
- Discovery limitata a figli diretti della directory casi configurata, che deve restare nel repository. I manifesti sono limitati a 64 KiB; il validatore rifiuta ID non portabili o discordanti, campi sconosciuti, pesi non finiti, path assoluti/Windows/traversal, path dichiarati sovrapposti, attraversamento di symlink e symlink della fixture che escono dal caso.
- `case create` usa una directory di staging interna e una rinomina atomica, rifiuta target esistenti e non sovrascrive casi.
- `case validate` controlla il protocollo JSON del grader, ID check univoci, massimo e somma punti a 100, intervalli earned, coerenza score e fixture iniziale sotto 60.
- `thinking_challenge` usa soltanto dati sintetici, valuta un risolutore esatto tramite comportamento osservabile e scenari alternativi nel grader, e non richiede né premia una traccia di reasoning. Una regressione dimostra che l'hardcode dell'esempio pubblico resta sotto la soglia; una soluzione generica di calibrazione raggiunge 100/100.
- Preflight Git obbligatorio per gli input selezionati: file modificati o non tracciati in `AGENTS.md`, `.gitignore`, manifesti, prompt, fixture, grader o rubriche bloccano il run.
- Snapshot condiviso creato una sola volta prima della matrice usando soltanto file tracciati da Git, con esclusione di cache/output ignorati e SHA-256 separati per istruzioni, policy di esecuzione, manifesto, prompt, fixture, grader, rubrica e input effettivo complessivo.
- Ogni workspace registra commit e tree Git della baseline; input o baseline divergenti vengono rilevati dal report.
- Nessuna dipendenza Python di runtime e nessun download automatico di modelli.
- Ogni versione Pi, inclusa la 0.85.1, deve superare prima delle task un controllo del payload reale su un server OpenAI-compatible sintetico vincolato a `127.0.0.1`. Il probe usa prompt fissi, directory Pi isolate, `--offline`, tool disabilitati e timeout configurabile; verifica thinking `off`/`medium`, limite token, eventi, errore terminale e assenza di retry. Esegue il backend sandbox selezionato, compreso lo staging AppContainer Windows quando richiesto. Nessun payload, risposta o errore libero del probe viene salvato nei risultati: solo versione del contratto, stato e codice del controllo fallito. Pi 0.85.1 è suggerita come riferimento in caso di errore, senza downgrade automatico.
- Every Pi version, including 0.85.1, must pass the real-payload contract check before tasks. A synthetic OpenAI-compatible server binds only to `127.0.0.1`. The probe uses fixed prompts, isolated Pi directories, `--offline`, disabled tools, a configurable timeout, and the selected sandbox. It checks `off`/`medium` thinking, token limits, events, terminal errors, and retries. Only sanitized status, contract version, and failed-check code are retained; no probe payload or free-form error is persisted. Pi 0.85.1 is suggested as a reference if the check fails, without automatic downgrade.
- Pi viene avviato con `--offline`, telemetria disabilitata e risorse globali non necessarie disabilitate; la policy bilingue preposta al prompt vieta rete e path esterni.
- `PI_CODING_AGENT_DIR` punta a una directory nuova per ogni task; il file provider contiene solo un placeholder locale, non una chiave reale. Una task non può quindi alterare la configurazione Pi di quella successiva.
- La policy thinking canonicalizza il livello richiesto in un valore esplicito (`off` → `none`) senza fallback. Ollama usa `/api/show`, LM Studio espone metadati propri e llama.cpp può non dichiarare la capability; il preflight per modello usa lo stesso endpoint OpenAI-compatible e lo stesso `reasoning_effort` delle task. Modalità attive senza reasoning osservabile e modalità `off` che espongono reasoning falliscono chiuso.
- `models.json` ripete il controllo in `samplingParams`, dichiara `supportsReasoningEffort` e `maxTokensField`; `settings.json` disabilita il timeout HTTP idle e i retry agente/provider. Retry osservati quando configurati a zero e thinking osservabile in `off` escludono l'intero modello. Preflight e warmup sono separati dalle metriche task; il warmup usa la stessa modalità sul provider selezionato.
- Ogni tentativo parte da una copia nuova e da un commit Git baseline; `.benchmark-scratch/` è interna, ignorata in Git e assegnata a `TMPDIR`, `TMP` e `TEMP`.
- Prima e dopo ogni task vengono confrontati i file Git tracciati e non ignorati del repository; le mutazioni attribuibili alla task invalidano il modello.
- L'audit versionato risolve path strutturati e argomenti shell rispetto alla workspace e ai cambi `cd` deterministici, riconosce path assoluti POSIX e Windows indipendentemente dal sistema host, distingue traversal confinati nello scratch da target esterni, protegge l'intera root del benchmark e riconosce comandi o codice di rete comuni. Dalla versione audit 3 separa i payload heredoc letterali dal controllo shell, continuando però a esaminare rete negli heredoc consegnati a interpreti. La versione audit 4 segue anche i separatori di riga e le variabili `$PWD`/`$OLDPWD` nei cambi directory, evitando di scambiare un traversal interno allo scratch per un accesso esterno; una violazione reale esclude l'intero modello dalla classifica.
- The versioned audit resolves structured paths and shell arguments against the workspace and deterministic `cd` changes, recognizes POSIX and Windows absolute paths on every host, and distinguishes scratch-confined traversal from external targets. Audit version 3 separates literal heredoc bodies from shell control while checking network code passed to interpreters. Version 4 also tracks line separators and `$PWD`/`$OLDPWD` across directory changes, so an internal scratch traversal is not mistaken for an external access; genuine violations disqualify the entire model.
- Il report mostra motivo, target ed evidenza delle violazioni e può riesaminare eventi di audit precedenti senza riscrivere i `result.json` originali.
- Lo snapshot viene ricontrollato prima e dopo ogni task; se cambia, il grader non viene eseguito e la matrice si interrompe.
- Ordine task randomizzato con seed registrato; unload e warmup sono ripetuti a ogni cambio modello.
- Timeout per task e terminazione del gruppo processo su sistemi POSIX.
- Gli eventi JSONL vengono controllati anche per un errore terminale agente/provider: il runner assegna `pi_error` anche se il processo Pi esce con codice zero, registrando nei metadata soltanto un indicatore booleano. Il testo libero resta negli artefatti locali e non entra nell'export dashboard.
- Grader eseguiti come processi separati, con timeout e senza scrittura di bytecode.

## Segreti e logging / Secrets and logging

Il benchmark non richiede API key. Non inserire token, password, repository privati o documenti personali nei prompt o nelle fixture. Gli eventi JSONL di Pi possono contenere integralmente prompt, risposte, blocchi di reasoning, comandi, output tool e frammenti di file. Il preflight scarta la risposta e conserva soltanto stato/durata/conteggi; report ed export non contengono la traccia di reasoning. Trattare comunque l'intera directory `results/` come potenzialmente sensibile.

The benchmark requires no API key. Do not place tokens, passwords, private repositories, or personal documents in prompts or fixtures. Pi JSONL events may contain complete prompts, responses, reasoning blocks, commands, tool output, and file excerpts. Preflight responses are discarded and only status/duration/counts are retained; reports and dashboard exports contain no reasoning trace. Treat all of `results/`, including `guided-run.json`, as potentially sensitive. Guided manifests and dashboard exports still expose local model names, case titles, scores, timings, settings, and hashes that can be linked to retained source runs; review them before sharing.

## Rete / Network

Il runner non contatta servizi Internet. `--offline` disattiva le operazioni di rete iniziali di Pi, mentre le richieste al provider configurato restano locali. La policy vieta la rete e l'audit registra pattern espliciti come `curl`, `wget`, operazioni Git remote e chiamate Python HTTP/socket note. Seatbelt su macOS nega tecnicamente l'outbound salvo la porta loopback del provider. Su Linux il processo confinato non condivide la rete host e raggiunge il broker solo tramite socket Unix; su Windows AppContainer non riceve capability di rete e raggiunge il broker solo tramite named pipe. I broker sono processi host fidati vincolati all'unica destinazione configurata. In modalità `audit` e nel fallback di `auto`, l'audit non è un firewall.

The runner does not contact Internet services. Pi startup networking is disabled, while required traffic to the configured provider remains local. The policy forbids networking, and the audit records explicit patterns such as `curl`, `wget`, remote Git operations, and known Python HTTP/socket calls. Seatbelt on macOS technically denies outbound connections except the provider's loopback port. On Linux, the confined process does not share host networking and reaches the broker only through a Unix socket; on Windows, AppContainer receives no network capabilities and reaches it only through a named pipe. Brokers are trusted host processes pinned to the single configured destination. In `audit` mode and the `auto` fallback, the audit is not a firewall. `dashboard-data` performs only local file reads and writes; candidate and official dashboards use local data and assets without telemetry or remote APIs. The official launcher creates a temporary HTTP surface only on `127.0.0.1`, protected by a fixed route whitelist and a `connect-src 'none'` CSP.

La visita alla landing scarica i soli asset statici dallo stesso origin Pages. Repository, release, licenza e sito personale vengono contattati soltanto dopo una navigazione esplicita dell'utente; nessun dato del benchmark viene trasmesso automaticamente. / Visiting the landing page downloads static assets from the same Pages origin only. The repository, release, license, and personal website are contacted only after explicit user navigation; no benchmark data is transmitted automatically.

Il percorso guidato limita ogni provider a `127.0.0.1`, `localhost` o `::1` e la dashboard a `127.0.0.1`. Non aggiunge telemetria o Internet; eredita i controlli e i limiti di rete del runner. / The guided path accepts every provider only on `127.0.0.1`, `localhost`, or `::1` and keeps the dashboard on `127.0.0.1`. It adds no telemetry or Internet access and inherits the runner's network controls and limitations.

## Filesystem e permessi / Filesystem and permissions

Pi riceve strumenti `read`, `bash`, `edit`, `write`, `grep`, `find` e `ls` perché le task richiedono modifica e test. Il working directory è confinato logicamente alla fixture e lo scratch previsto resta sotto quella root; gli sconfinamenti espliciti vengono sempre auditati. Con un backend applicato, Pi e i figli vengono inoltre limitati dal sistema operativo; in `audit-only` ereditano ancora i permessi dell'utente.

Pi receives file and shell tools because tasks require editing and testing. Its working directory is logically scoped to the fixture, and the designated scratch area remains under that root; explicit escapes are always audited. When a backend is applied, the OS additionally restricts Pi and its children; in `audit-only` mode they still inherit the user's permissions.

Il launcher ufficiale legge `run.json` e `report.json` soltanto dai run confinati selezionati, oppure un export pubblico già validato, e non scrive nelle sorgenti. La sola scrittura possibile è la generazione esplicita e atomica di `dashboard/data/snapshot.js`, output locale ignorato da Git; il normale avvio non crea file. Il file chooser è gestito dal browser e non concede al server accesso arbitrario al filesystem.

The official launcher reads `run.json` and `report.json` only from selected confined runs, or an already validated public export, and never writes to sources. Its only write operation is explicit atomic generation of `dashboard/data/snapshot.js`, a local Git-ignored output; normal startup creates no file. The browser handles file selection and does not grant arbitrary filesystem access to the server.

La landing non dispone di API filesystem né di file chooser. L'anteprima locale legge soltanto `site/`; il deploy Pages riceve un artefatto composto esclusivamente da quella directory. / The landing page has no filesystem API or file chooser. Local preview reads only `site/`; Pages deployment receives an artifact made exclusively from that directory.

La GUI scrive soltanto preferenze validate in `.localagent-benchmark/` e sessioni sotto la `dashboard.results_directory` configurata. Non sovrascrive directory esistenti e non cancella risultati. Il riavvio della dashboard risolve solo path relativi confinati registrati nel manifesto. / The GUI writes only validated preferences under `.localagent-benchmark/` and sessions under the configured results directory. It neither overwrites existing directories nor deletes results. Dashboard reopening resolves only confined relative paths recorded in the manifest.

## Validazione e processi / Validation and processes

I grader sono codice fidato versionato e vengono eseguiti dalla copia congelata soltanto dopo la verifica del relativo hash. Anche `case validate` esegue il grader per controllarne protocollo e calibrazione. Nessuna delle due esecuzioni usa il backend sandbox e entrambe mantengono i permessi dell'utente: ispezionare integralmente un caso importato prima di caricare la configurazione per un run o lanciare la validazione, e non aggiungere grader provenienti da terzi senza revisione. I file JSON dei risultati sono prodotti localmente e non devono essere usati come comandi. Il report effettua rendering Markdown di nomi modello locali; aprirlo solo in viewer fidati se i nomi provengono da un server Ollama non controllato.

Il launcher guidato e la dashboard sono processi host fidati. Su POSIX la cancellazione segnala il nuovo process group; su Windows usa un process group dedicato e `taskkill /T /F`. Questa gestione riduce i processi orfani ma non è una sandbox e può fallire in caso di crash del sistema o restrizioni della piattaforma. / The guided launcher and dashboard are trusted host processes. Cancellation targets the new process group on POSIX and uses a dedicated group plus `taskkill /T /F` on Windows. This reduces orphaned children but is not a sandbox and may fail after system crashes or platform restrictions.

Per ogni avvio Pi su Windows, il runner tenta di assegnare il launcher e i suoi discendenti a un Job Object con terminazione alla chiusura, anche in modalità `audit`. Timeout, cancellazione e uscita normale chiudono il Job Object; se l'assegnazione non riesce, il cleanup usa `taskkill /T /F` e limita comunque l'attesa finale delle pipe. Su POSIX il cleanup segnala il process group anche se il launcher è già uscito. Questi controlli servono a fermare i processi del benchmark, non isolano filesystem o rete; restrizioni dell'host o un crash possono ancora lasciare processi figli da verificare manualmente. / On Windows, each Pi launch attempts to place its launcher and descendants in a kill-on-close Job Object, including in `audit` mode. Timeouts, cancellation, and normal completion close it; if assignment fails, cleanup uses `taskkill /T /F` and still bounds final pipe collection. On POSIX, cleanup signals the process group even if the launcher already exited. This process cleanup does not isolate files or networking; host restrictions or crashes can still leave descendants requiring manual inspection.

## Limiti residui / Residual risks

- `audit` e il fallback di `auto` non applicano isolamento OS; il manifesto lo segnala esplicitamente.
- `sandbox-exec` è deprecato da Apple e può essere assente o rifiutare il probe; il backend non usa l'App Sandbox firmata. Directory runtime di sistema restano leggibili e la policy deve essere rivalidata dopo aggiornamenti macOS/Pi.
- Bubblewrap richiede user e network namespace non privilegiati. Policy kernel o AppArmor più restrittive possono far fallire il probe; `required` si ferma invece di degradare. Directory runtime necessarie come `/usr` e `/etc` restano leggibili.
- AppContainer deve poter creare il profilo e modificare temporaneamente le ACL dei path autorizzati. Un arresto anomalo del launcher può lasciare profilo o ACE da diagnosticare e rimuovere; il runtime staged occupa temporaneamente spazio nella directory della task e le normali semantiche registry di AppContainer non equivalgono a un registry vuoto.
- Il broker limita la destinazione di rete ma non autentica, autorizza o filtra semanticamente il protocollo del provider. Un difetto nel broker host attraverserebbe il confine del sandbox.
- L'audit post-run non è un reference monitor: comandi shell costruiti dinamicamente, espansioni non deterministiche, semantiche complesse o codice offuscato possono leggere file esterni o usare la rete senza includere un indicatore riconoscibile negli argomenti registrati; euristiche future possono anche richiedere calibrazione contro nuovi falsi positivi.
- Il confronto del repository rileva scritture a file tracciati o non ignorati, ma non letture e non file creati in aree ignorate diverse dalla directory del run.
- Le mutazioni alle sorgenti vengono rilevate e attribuite, ma non ripristinate automaticamente per preservare prove e modifiche utente; occorre revisione prima del run successivo.
- Nessun blocco di rete a livello kernel in `audit` o nel fallback di `auto`.
- Linux usa PID namespace e `die-with-parent`, Windows un Job Object kill-on-close e macOS il gruppo processo; arresti del sistema o difetti del runtime possono comunque impedire la pulizia ordinata.
- Un grader difettoso o malevolo ha accesso ai permessi dell'utente.
- Lo schema e i controlli di path non analizzano il comportamento del codice Python del grader; un manifesto strutturalmente valido può comunque accompagnare codice malevolo.
- Log e workspace possono occupare molto spazio o contenere dati che il modello ha letto.
- I modelli locali e i runtime provider sono supply-chain esterne al repository.
- Il preflight dimostra soltanto il comportamento osservabile dell'endpoint per una richiesta minima. Non prova processi interni non esposti; modelli che non espongono reasoning in modalità attiva vengono esclusi come non verificabili. Capability `thinking` non dimostra da sola che `off` sia supportato.
- Gli scenari alternativi di `thinking_challenge` sono un controllo anti-hardcoding, non un confine di segretezza. In modalità `audit` un agente conserva tecnicamente i permessi dell'utente, ma un tentativo esplicito di leggere il grader fuori workspace è una violazione d'integrità; usare `--sandbox required` quando questa separazione deve essere applicata dal sistema operativo.
- Il gate Pi verifica il contratto osservabile a ogni avvio, ma non può provare ogni comportamento di una nuova versione: servono smoke reali per le piattaforme e il tool calling. I runtime provider possono cambiare semantica: le versioni registrate e la provenienza modello fanno parte dei controlli di comparabilità.
- Un modello può ancora tentare di manipolare `.git` nella propria workspace; grader e snapshot restano fuori dalle mount consentite, ma l'audit e gli hash continuano a essere necessari come controllo indipendente.
- Le metriche POSIX possono non includere completamente tutti i discendenti; i contatori RAPL sono host-wide, possono includere altri carichi e spesso non sono disponibili senza permessi aggiuntivi.
- La whitelist dashboard riduce i dati ma non anonimizza nomi di modelli/casi, metriche o hash. Un nome locale può essere sensibile e gli hash possono collegare l'export ai run conservati.
- Il grader statico/Node della dashboard non sostituisce un browser reale: richieste costruite dinamicamente, problemi responsive o difetti di accessibilità possono richiedere ispezione manuale. La pubblicazione della dashboard non è automatica.
- Il binding loopback impedisce l'esposizione diretta in LAN ma non protegge da altri processi locali, estensioni browser o malware eseguiti con l'account utente. Uno snapshot generato localmente resta leggibile dagli altri processi autorizzati sullo stesso sistema e deve essere revisionato prima di qualsiasi condivisione manuale.
- La CSP e la whitelist riducono la superficie HTTP, ma le restrizioni `file://` variano tra browser; il launcher loopback resta il flusso raccomandato.
- Su GitHub Pages la CSP è fornita tramite elemento `meta`: non può esprimere direttive riservate agli header, e gli header di piattaforma restano sotto il controllo dell'host. Un link esterno rivela normalmente destinazione, indirizzo IP e metadati di navigazione al sito raggiunto. / On GitHub Pages the CSP is delivered through a `meta` element, so it cannot express header-only directives and platform headers remain controlled by the host. Following an external link normally reveals destination, IP address, and navigation metadata to that site.
- Qualunque file aggiunto in futuro a `site/` diventa pubblico al deploy. I controlli automatici rilevano pattern noti, non sostituiscono la revisione umana di testo e immagini e non provano da soli contrasto, layout o comportamento di estensioni browser. / Any file later added to `site/` becomes public on deployment. Automated checks detect known patterns but do not replace human review of text and images or prove contrast, layout, and browser-extension behavior.
- I launcher guidati sono script sorgente non firmati, non installer o app native. La disponibilità di Tkinter, l'associazione del doppio clic e gli avvisi Gatekeeper/SmartScreen dipendono dall'installazione locale; Linux varia per file manager.
- La cancellazione conserva una sessione diagnosticabile ma non offre resume della fase interrotta. Un crash immediato può lasciare un processo figlio che richiede verifica manuale; il manifesto locale può contenere path relativi, nomi modello e messaggi d'errore.

## Raccomandazioni / Recommendations

- Eseguire con account non privilegiato e fixture esclusivamente sintetiche.
- Usare `--sandbox required` per impedire fallback quando l'isolamento è requisito del run.
- Non disabilitare policy kernel/AppArmor aziendali solo per far passare il probe Linux: usare un host approvato o accettare esplicitamente `audit`/fallback per dati esclusivamente sintetici.
- Revisionare manifesto, prompt, fixture, grader e rubrica prima di `case validate` e di ogni run.
- Non ignorare errori `inputs`, `violations_detected` o `snapshot_compromised` e non reinserire manualmente modelli esclusi nella classifica.
- Cancellare in modo consapevole i risultati non più necessari e non pubblicarli senza revisione.
- Mantenere Pi e il provider scelto aggiornati solo attraverso fonti verificate; registrare le versioni per confronti longitudinali.
- Non modificare il default loopback in un endpoint remoto senza consenso esplicito e documentazione dei dati inviati.
- Ispezionare `dashboard-data.json` prima di congelarlo o condividerlo; mantenere il file e le dashboard candidate locali finché non è stata completata la revisione visuale, di rete e privacy.
- Tenere `dashboard.host` su `127.0.0.1`, lasciare la porta automatica salvo necessità e chiudere il launcher con `Ctrl+C` quando la consultazione è terminata.
- Rigenerare lo snapshot ufficiale soltanto da una fixture pubblica revisionata e verificare il diff e la suite Node prima del commit.
- Prima di ogni deploy Pages, revisionare l'intero contenuto di `site/`, verificare che non includa risultati o sorgenti locali, eseguire test e controllo browser desktop/mobile, quindi ispezionare il dominio Network per confermare l'assenza di richieste inattese. / Before every Pages deployment, review all of `site/`, confirm it contains no results or local sources, run automated and desktop/mobile browser checks, and inspect the Network panel for unexpected requests.
- Mantenere le azioni del workflow Pages fissate a commit revisionati e abilitare/pubblicare Pages soltanto dopo l'approvazione prevista dal piano. / Keep Pages workflow actions pinned to reviewed commits and enable or publish Pages only after the approval required by the plan.
- Avviare il percorso guidato soltanto da un checkout revisionato, verificare i modelli e le impostazioni mostrate prima della conferma e non condividere una directory `guided-*` senza averne ispezionato manifesto e run.
